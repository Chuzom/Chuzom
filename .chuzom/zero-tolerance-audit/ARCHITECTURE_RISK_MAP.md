## 3. North Star coherence (mandate item 5)

`Docs/planning/NORTH_STAR.md` states (verbatim): *"'most capable' is defined by the live external model leaderboard, not by any one vendor... It is read from a continuously-updated external ranking: https://artificialanalysis.ai/leaderboards/models... Pinning 'Claude = top' is a North-Star violation the moment another model leads."*

**This is not what the runtime does.** `src/chuzom/benchmark_fetcher.py`'s own module docstring: *"Offline benchmark data fetcher — runs in GitHub Actions, never at runtime... This module requires the `scripts` optional dependency group."* It fetches from Arena Hard Auto, Aider, HuggingFace Open LLM Leaderboard v2, and LiteLLM pricing, then writes a static `src/chuzom/data/benchmarks.json` that ships bundled with the package.

**Confirmed by reading the actual bundled file at HEAD:** `data/benchmarks.json` → `"generated_at": "2026-03-30T15:30:35Z"`. Relative to the current audit date (2026-08-11), the "continuously-updated" leaderboard the runtime actually consults is **over 4 months stale**, and no runtime staleness check or user-facing warning was found in `model_registry.py` (`grep -n "stale" model_registry.py` → zero hits).

**Direct answers to the mandated North Star questions:**
- **Is "capable" computable from available information?** Yes, mechanically — `model_registry.py`/`benchmarks.json`/`dynamic_routing.py` do produce a tier ordering. But it is computed from a periodically-regenerated static snapshot, not a live signal, contradicting the document's own framing.
- **Is the leaderboard live by default, or optional/disabled?** Optional and offline by design (`[scripts]` extra, GitHub-Actions-only). At runtime it is never fetched; it is read from a committed, potentially stale file.
- **What happens when unavailable?** Silent — the bundled `benchmarks.json` is used with no visible warning that it may be stale, because there is no live fetch to fail in the first place; the failure mode is "silently stale," not "silently unavailable."
- **Cheapest — raw cost, subscription marginal cost, quota cost, latency, failure probability, retry cost, or quality-adjusted total expected cost?** The codebase mixes several of these concepts without a single reconciling function: `cost.py` computes dollar-cost baselines; `execution_ledger.py` separately tracks `baseline_tokens` explicitly described in a router.py comment as "the actual_proxy for quota-tokens-saved... in place of a fabricated $ baseline" for subscription/host_mode — i.e. the codebase itself acknowledges, in-line, that "dollar savings" and "quota/token savings" are different, non-interchangeable metrics, and both are surfaced under variations of the same "saved_usd"/"savings" label to the user.
- **Cheapest-initial-attempt vs. minimum-expected-cost-of-successful-completion?** The `ESCALATE` step in the documented pipeline (NORTH_STAR.md step 6) exists and is real (confirmed present in router.py's retry/escalation logic), so the *mechanism* for expected-cost-of-completion exists. But the savings/ledger accounting audited above computes savings per **accepted attempt only** (`event_type="attempt_completed", accepted=True`) — rejected/failed attempts are tracked "cost-only" per the router.py comment ("R6 — rejected attempts above stay cost-only"), meaning the *reported* savings figure does not net out the cost of prior failed/escalated attempts against the eventual success. A cheap model that fails 40% of the time and gets retried will show an "accepted-attempt savings" figure that does not reflect the true expected cost of the whole escalation chain, unless every downstream consumer of `saved_usd` also separately nets in `failed_attempt_cost_usd` (present as a field, but whether every one of the ~26 consumer files actually subtracts it was not exhaustively verified this pass).
- **Aspirational vs. current behavior?** **Aspirational, presented as current.** The document's present-tense, declarative claims ("is read from," "continuously-updated," "must track this leaderboard") describe a live system; the actual implementation is an offline, CI-only, manually-triggered snapshot process with no runtime staleness signal. This is the same shape of gap the document itself calls out as a violation ("claims a guarantee that isn't measured" — NORTH_STAR.md's own anti-goals list) — applied reflexively, the document violates its own anti-goal #5.

## 4. Product-value challenge (mandate item 6)

Honest assessment, given everything found above:

- **Where Chuzom plausibly wins:** high-volume, low-stakes Q&A/analysis offload where a wrong or 3x-mis-costed savings figure has no correctness consequence for the user's actual work product — e.g., routing a simple lookup to a local Ollama model genuinely avoids spending a Claude-subscription turn, independent of whether the *displayed savings number* is accurate. The routing mechanism itself (classify → route → execute → verify → escalate) is real and exercised; the North Star's *operational* pipeline exists even where its *leaderboard-freshness* claim does not.
- **Where Chuzom breaks even:** tasks where classification is ambiguous across the three independent classifiers (Cluster D) — a prompt that `auto-route.py` correctly recognizes as needing tools but that `agent-route.py`'s cruder regex-scorer defaults to `analyze` for (its no-signal fallback) risks being routed to a no-tools completion door for what is actually an execution task — precisely the failure mode NORTH_STAR.md's own anti-goals list names first ("Enforcing a completion tool on a task that needs to run tools — a structural dead-end"). A developer using Claude Code directly does not have this three-classifier disagreement risk at all.
- **Where Chuzom loses:** any workflow where the user or team makes decisions based on the **displayed savings/cost figures** — budget reporting, "how much did routing save us this month," ROI justification to a manager, or `commands/gain.py`/`commands/explain_dashboard.py` output. Given the proven 3x live inflation on research/complex-task savings via `dashboard_data.py` and `cost.py::BASELINE_PRICING`, and the structurally-guaranteed disagreement between the ledger and receipt savings numbers for the same event (§4 of `03_ARCHITECTURE_MAP.md`), a user trusting these numbers today is trusting figures this audit can prove are wrong by a known, reproducible, non-trivial factor. A developer who instead just used Claude Code/Codex/Gemini directly, with no savings dashboard, would not be exposed to this specific failure mode — because they would not be shown a wrong number that looks authoritative.
- **Task class where Chuzom should deliberately bypass itself:** any request whose primary deliverable *is* a cost/savings figure (financial reporting, budget review, "prove routing worked") — until the pricing-table duplication (`03_ARCHITECTURE_MAP.md`) is collapsed to one canonical, imported-everywhere source with a CI lint equivalent to `scripts/lint_tool_surface.py`, Chuzom should not present itself as authoritative for exactly the number it is built to optimize.
- **Routing machinery ≠ automatic value, stated plainly:** the presence of a classifier, a router, an escalation ladder, and a savings ledger does not by itself prove the system delivers what it reports. This audit found the routing *execution* path (get a cheaper model to do the work) is real and mechanically sound in the files inspected, while the routing *accounting* path (prove that it was worth it, in dollars) is provably wrong today on a well-defined, reproducible class of calls. A tool that silently overstates its own value by 3x on exactly the metric it exists to sell is a governance risk independent of whether the underlying routing decisions are themselves good.
